# gtm-apply Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn this repo into a versioned, installable package that every Tag Manager customer repo imports, so that provisioning a container is one JSON spec in the shape of a GTM container export plus one apply command, and setting up conversions for a new customer is a short config that compiles to that spec.

**Architecture:** Three layers. Layer 1 is the existing `GtmClient` (auth, token persistence, throttled raw `tagmanager_v2` service). Layer 2 is resource helpers: container resolution, workspace reuse, and name-keyed idempotent upserts for folders, variables, triggers, and tags. Layer 3 is the spec engine: a `ContainerSpec` type derived from the API's `ContainerVersion` schema, a normalizer that turns a UI export into a spec, a planner that resolves every reference and reports every problem before any write, and an executor that applies the plan in dependency order. Recipes (GA4 event, Google Ads conversion) are pure functions that compile to spec fragments and go through the same engine.

**Tech Stack:** TypeScript 5 (strict, ESM, NodeNext), `@googleapis/tagmanager` (per-API generated client, `tagmanager_v2` namespace), `google-auth-library`, Node 18+, pnpm, vitest, husky + lint-staged + prettier.

**Spec:** This document. The "Design" section records the design discussions of 2026-09-09 and is the spec the tasks implement.

## Design

### Why a package

Tag Manager work recurs across customer repos. Each one today would copy the OAuth flow and re-derive the API calls. A single versioned package owns auth and the API surface; customer repos carry only a spec file or a short config and a script. Bugs get fixed once, and the onboarding sequence becomes reviewable and repeatable.

### Layering

| Layer | Responsibility | Status |
|---|---|---|
| 1. Client | OAuth local-server flow, token persistence and refresh, raw `tagmanager_v2` service, throttle and retry | Exists as `GtmClient`; needs shared credential location, retry, test seam, dependency swap |
| 2. Resource helpers | Resolve `GTM-XXXX` to a container; create-or-reuse workspace; `ensureFolder`, `ensureVariable`, `ensureTrigger`, `ensureTag` upserts by name with fingerprint handling; enable built-in variables | Not started |
| 3. Spec engine | `ContainerSpec` type, `normalizeExport`, `planContainerSpec`, `executePlan`, `applySpec` | Not started |
| 3b. Recipes | `ga4Event`, `googleAdsConversion`, trigger recipes, `compileConversions`, `applyConversions` | Not started |
| CLI | `gtm-apply apply`, `gtm-apply normalize`, `gtm-apply export` | Not started |

The raw service stays reachable as `client.service` so nothing the package does not wrap is blocked.

### Dependency: per-API generated client

The repo currently depends on `googleapis`, the monolithic bundle of every Google API. Installed it is 110 MB and it slows typechecking. Google generates and publishes the same code per API as `@googleapis/tagmanager`, which exports the same `tagmanager_v2` namespace and `Schema$*` types. The package depends on that package directly, not as a peer dependency, because customer repos never call the Tag Manager API themselves. The package re-exports the `tagmanager_v2` type namespace so consumers never install the Google package. `google-auth-library` is pinned to the same major that `googleapis-common` (pulled in by the per-API package) requires, so only one copy of `OAuth2Client` exists in the tree.

Per-API packages bump majors when Google regenerates them. Pin with a caret on the major and let the tests catch a breaking regeneration before a release tag.

### Shared credentials

`GtmClient` defaults today to files in the current working directory, which forces re-authorization per repo. The package defaults to `~/.config/gtm-apply/client_secrets.json` and `~/.config/gtm-apply/token.json`, overridable by `GTM_APPLY_CONFIG_DIR` and by constructor options. One Google account holds all customer permissions, so one token serves every repo.

### The spec is the export shape

The GTM UI's container export is the API's `ContainerVersion` resource serialized. Its `tag`, `trigger`, `variable`, `folder`, and `builtInVariable` arrays are the shapes the API accepts on create and update. The package's input type, `ContainerSpec`, is a subset of that shape with three normalizations:

1. **Server fields are stripped.** `accountId`, `containerId`, `workspaceId`, every `*Id`, `fingerprint`, `path`, `tagManagerUrl`. They are container-specific and never part of a spec.
2. **Id references become name references.** `firingTriggerId` and `blockingTriggerId` become `firingTriggerName` and `blockingTriggerName`. `parentFolderId` becomes `parentFolderName`. Variable and tag references inside parameters (`{{Name}}`, `tagReference`) are already by name and pass through unchanged.
3. **Enum casing is lower camel.** Exports write `TEMPLATE`, `CUSTOM_EVENT`, `EQUALS`, `ONCE_PER_EVENT`; the API reference documents `template`, `customEvent`, `equals`, `oncePerEvent`. The normalizer converts values under the keys `type`, `tagFiringOption`, `consentStatus`, and `caseConversionType`. It never touches `value` fields, since a constant's value can legitimately be upper snake case.

Benefits: the types come from `@googleapis/tagmanager` for free; a tag built once in the UI and exported is a recipe with the exact parameter keys the API wants; and the format interoperates with GTM import, Simo Ahava's GTM Tools, and the community YAML converters.

A spec file for a customer:

```json
{
  "variable": [
    { "name": "Const - Google Ads Conversion ID", "type": "c",
      "parameter": [{ "type": "template", "key": "value", "value": "AW-123" }] }
  ],
  "trigger": [
    { "name": "Custom Event - lead", "type": "customEvent",
      "customEventFilter": [{ "type": "equals", "parameter": [
        { "type": "template", "key": "arg0", "value": "{{_event}}" },
        { "type": "template", "key": "arg1", "value": "lead" } ] }] }
  ],
  "tag": [
    { "name": "Ads - Lead", "type": "awct", "firingTriggerName": ["Custom Event - lead"],
      "parameter": [
        { "type": "template", "key": "conversionId", "value": "{{Const - Google Ads Conversion ID}}" },
        { "type": "template", "key": "conversionLabel", "value": "xyz" } ] }
  ]
}
```

Customer-specific values live in constant variables that tags reference by name. That keeps exported fragments customer-agnostic, uses GTM's own variable syntax instead of a second templating layer, and means one golden export serves every client.

### Plan, then execute

Applying a spec is two phases. `planContainerSpec` reads the target workspace, resolves every reference, and produces a list of operations (`create`, `update`, `unchanged`) plus a list of errors. `executePlan` refuses to run while the plan has errors. `dryRun` is the plan printed and nothing else, so what the dry run shows is exactly what apply does.

### What gets created implicitly

There is no `autoCreate` option. One rule: if an entity needs no information beyond its name, the engine creates it and marks the operation `implicit` in the plan. If it needs a value or a type, it must be in the spec.

- **Workspace:** created by name if missing. Always, because the default workspace is off limits.
- **Folders:** a `parentFolderName` that matches no folder in the spec or the container is created.
- **Built-in variables:** a `{{Page Path}}` or `{{Form ID}}` reference that matches no variable is looked up in the built-in catalog and enabled.
- **Container:** never implicit. `createContainer()` exists as an explicit helper for onboarding a customer who has no container yet.

Everything else fails in the plan phase, listed all at once:

```
Plan has 2 errors:
- tag "Ads - Lead" fires on trigger "Custom Event - lead", which is not in the spec or the container
- {{Const - GA4 ID}} is referenced but is not in the spec, the container, or the built-in catalog
```

### The engine owns ordering

Spec authors never order entities. The executor applies folders, then variables, then triggers, then tags, and resolves names to ids after each tier lands. Within variables, a variable may reference another variable, so the planner sorts that tier by its `{{ }}` references and reports a cycle as an error. Exports come out of GTM in arbitrary order, and hand-edited specs must not break because of it.

### Pitfalls the design absorbs

- **Fingerprints.** Every update must send the entity's current fingerprint. The `ensure*` helpers fetch, compare, and update in one place.
- **Rate limits.** The Tag Manager API has tight per-user per-minute limits. `client.call` wraps every request with a throttle and retry with backoff.
- **Workspace caps.** Standard containers allow only a few concurrent workspaces. The engine reuses by name and never creates a second workspace with the same name.
- **Custom templates.** A tag built on a community or custom template has type `cvt_<containerId>_<templateId>`, bound to the source container. The normalizer rejects these with a clear message. Supporting them means importing the template first and remapping the type; that is a backlog item.
- **Trigger groups.** Parameters of type `triggerReference` hold trigger ids. The normalizer rejects them. Backlog item.
- **Diff scope.** The planner compares only the fields the spec provides. Fields stripped from an export, such as `monitoringMetadata`, are not corrected if someone changes them in the UI. Documented in the README.
- **Enum keys.** If the live API rejects a value the normalizer did not convert, add the key to the normalizer's enum-key set. The smoke test (Task 17) is where this surfaces.

### Prior art

Research on 2026-09-09 found no TypeScript package doing this. Closest: `kb223/gtm-ga4-sync` (Python CLI, YAML events to GA4 tags, dry run, never the default workspace, no publish, GA4 only) and `mirefly/terraform-provider-google-tag-manager` (Go, desired-state model, unmaintained since 2023). Borrowed from the former: the plan output labels (`[+]`, `[~]`, `[=]`, `[!]`) and community naming prefixes. Ad hoc, agent-driven edits are covered by the GTM MCP servers already connected in Claude sessions on this machine; this package covers repeatable, reviewable, spec-driven runs.

Backlog.md was adopted on 2026-09-09 (`backlog task list --plain`). Follow-up work goes there, not here; this document stays as the design record and the log of what was built.
